## 目标与背景

在 Ubuntu Server 的终端内输入命令后，直接进入全屏 TUI，持续查看本机硬件、指定 Docker 容器及已部署的 vLLM Chat、Embedding、Reranker 三类模型的状态与负载。不采集 LiteLLM 服务指标。方向键导航作用于下半区的服务与模型展示，模型选择同步更新上半区的关联 GPU 高亮；上半区持续显示硬件及 Docker 区域可容纳的容器状态，不直接接受方向键选择或滚动。`q` 退出，`t` 切换主题。

本期只做 TUI。保留禁用的 WebUI 服务入口，不实现 WebUI 采集或切换，不实现 Web 看板。采集失败仅在固定位置标记 `STALE`，错误详情写入独立文件日志，不进入 TUI。

### 已确认的范围决策

1. WebUI 保持禁用。首版左右键不切换到 WebUI，也不显示可访问的 WebUI 占位页。
2. vLLM 首版采集并显示三个已部署模型：Chat、Embedding、Reranker。三者持续采集，按模型类型展示对应指标；不采集 LiteLLM 服务指标。
3. Chat 延迟显示 TTFT 和 `Avg queue`；Embedding/Reranker 显示 `Avg queue` 和完成延迟 `Avg latency`，不套用 TTFT。均采用最近 60 秒窗口均值；无有效观测时显示 `—`，完成延迟的计时范围与处理单位须与来源一致。
4. Theme 仅由 `t` 切换，右上角显示主题名称但不可点击；默认 Moonlight，仅当前会话保留切换结果。
5. 磁盘显示指定挂载点的已用容量、总容量、使用率，默认 `/` 和 `/data`；不做磁盘读写速率。
6. 不实现 Details、Pause；删除设计稿中的 `Enter Details` 和 `p Pause` 提示与操作。
7. Docker 生命周期状态使用首字母大写、其余小写；配置数量不设固定上限，全部指定容器参与采集。显示时按配置顺序取区域可容纳的前若干项，其余不显示、不作任何提示，不截断或修改配置列表。
8. 采集失败只在预留状态位置显示 `STALE`，不显示最后成功时间、距今时长、错误原因或额外诊断信息，不改变布局。
9. 日志功能并入 REQ-001，只记录采集失败的 `ERROR` 信息。日志目录在 `config.yaml` 中自定义，默认 `~/.joi-observer/`，默认日志文件为该目录下的 `error.log`。
10. 优先保持现有 Neon Grid 布局；终端低于基础布局所需尺寸时提示放大窗口，不要求适配 80×24 或通过简化布局强行容纳。Docker 列表超出其区域容量仅隐藏后续条目，不触发放大提示。
11. 启动时日志目录/文件不可写，在进入 TUI 前提示一次后继续监控，暂不写日志，不以日志初始化失败阻断监控。
12. 同一监控对象的相同采集错误首次立即记录，持续失败时最多每 60 秒再记录一次；不同对象或新错误立即记录。
13. 首次安装提供示例 `config.yaml`，由用户先复制并修改；没有用户配置时提示所需配置路径并退出，不使用内置监控目标直接启动。
14. 模型与 GPU 关联高亮联动：选中模型关联的 GPU 使用主题主色，未关联的 GPU 使用灰色；切换模型只更新高亮，不过滤、重排 GPU 或改变布局、采样。映射仅来自显式配置或可靠数据，未知时不猜测。
15. 下半区的服务窗口、服务切换位及最底部键位提示合计固定占用全页面高度的一半；顶部品牌、主机信息和硬件区域等使用剩余上半区，不在两半之外额外占行。
16. Storage 固定 3 行内容，标题和边框另计；按配置顺序仅采集和显示前 3 个挂载点，其余忽略、不报错。Docker 面板高度随上半区右侧剩余空间伸缩，只显示可容纳的容器，内容少时允许留白；容纳不下的后续容器不显示，也不作任何提示。

### 共同业务规则

- **运行环境与边界**：首版目标为 Ubuntu Server 24.04 amd64、NVIDIA GPU。程序运行在被监控主机上，可由用户在终端或已有 SSH 会话中启动；程序不负责建立 SSH 连接或管理其他主机。当前 Windows 工作区不是实际采集环境。
- **只读监控**：不启动、停止、重启容器，不调整模型参数，不发送推理请求制造负载，不提供告警推送或服务管理。
- **执行限制**：遵守 `AGENTS.md` 的“禁止尝试连接任何服务器”。分析、设计和自动化验证使用本地材料与离线样本；本需求描述产品将来的采集行为，不构成实机连接或联调授权。
- **数据流**：沿用 `Collector → Monitor → MonitorState → TUI`。Monitor 统一写入独立内存状态，展示只读取快照。界面刷新、模型选择、主题切换不得引起重复采集。
- **实时与历史**：默认采样间隔 1 秒，可在启动配置中调整。各数据源独立更新；慢请求或失败不能阻塞键盘操作和其他来源。保留最近约 60 秒的有界历史，不建数据库，不持久化监控数据；REQ-001 的采集失败日志单独落盘，不保存正常采样值或历史曲线。
- **数据有效性**：有效值为 0 时正常显示 0；初始未采集、无有效观测或不支持的字段使用 `—`，模型类型不适用的字段省略或在固定槽位显示 `N/A`。采集失败可保留最后值，无历史有效值则显示 `—`，并在对应对象或面板的预留状态位仅显示 `STALE`。不显示最后成功时间、距今时长、错误原因、错误代码、异常堆栈或额外诊断提示；不得把失败伪装成正常的 0。内部仍保存采样时间，用于计算速率、窗口和数据有效性，不将其作为 UI 诊断信息展示。
- **异常与日志分离**：真实采集失败按 REQ-001 记录 ERROR，TUI 不展示日志或故障详情。已知不支持/不适用的指标、正常无负载、未配置监控对象以及成功查到的容器停止状态不属于采集失败，不因此记录错误日志。
- **页面分区**：以终端可用绘制区域的总高度为基准，下半区固定占一半，包含服务窗口自身的标题/边框、模型列表与指标/历史、vLLM/WebUI 切换位、最底部键位提示及这些元素之间的留白。上半区使用剩余高度，包含顶部品牌、主题、主机信息/时间、GPU、Host Resources、Storage、Docker 及相应边框和间距。页高为奇数时下半区向下取整，上半区获得多出的 1 行；不能先扣除页眉/页脚后再对剩余区域平分。
- **布局稳定**：同一终端尺寸和配置下，采集正常、失败、恢复及模型类型切换均不改变主要分区、指标区和历史图的高度。状态文字复用预留位置，不换行扩展、不弹窗、不新增错误面板；字段省略也不使区域收缩。Storage 内容区始终 3 行；Docker 面板填充上半区右侧扣除 Host Resources、Storage、边框及间距后的剩余高度，可见内容行数为配置容器数与区域可容纳行数的较小值，余高可留白。窗口缩放时上下两区仍按一半分配，Docker 随可用余高调整显示数量；采集状态变化不改变面板高度或可见对象顺序。
- **隔离与恢复**：单 GPU、单挂载点、Docker 或单模型异常不使整个界面退出；后续成功采集自动恢复。字段缺失仅影响该字段。历史中的失败区间保留缺口，不补成 0 或延续为新的有效观测。
- **无负载与无观测**：成功且可比较的采样区间没有 Token 或已完成处理单元增量时，对应吞吐为 0；没有延迟观测时，延迟为 `—`，不能显示 0 秒。首次采样、计数器重置或无可用基线时，不生成负速率或虚假峰值。
- **配置方式**：启动时读取用户准备的 YAML 格式 `config.yaml`，指定采样间隔、挂载点、容器、模型及其采集地址和日志设置，无需改源码。挂载点仅取前 3 项，其余忽略；容器列表不设固定数量上限，全部纳入且保持配置顺序，不修改原配置文件。随工具提供示例，首次使用先复制并修改；缺少配置时在进入全屏前提示所需路径并退出，不自动使用示例中的目标启动采集。首版不要求配置热重载、自动扫描模型、自动读取 Compose 或网关路由。配置文件查找顺序、字段结构及采集超时机制由 R2 明确；日志默认目录采用 `~/.joi-observer/`，不依赖 XDG 目录选择。
- **规模与终端**：以文档中的 5 GPU、默认 2 挂载点（最多显示 3 个）为主要布局场景，GPU 数量从实际采集结果获得，不硬编码为 5；Docker 配置数量不限，容器总数不提高页面最小高度。按上下各半及必要面板结构核算基础可用尺寸，不要求适配 80×24；低于基础尺寸时显示简短英文放大窗口提示，`q` 仍可退出，恢复后正常显示。Docker 列表超出其区域的条目只在显示层隐藏，不触发整页或局部放大提示，不影响其他面板，不挤占下半区；隐藏条目仍参与采集。模型列表超出可视区时随选择滚动；方向键不直接选择或滚动上半区，模型选择仅联动 GPU 高亮，不新增 Docker 滚动或分页。Storage 超出前 3 项仍按原规则忽略采集和显示。R2 须区分基础布局不足与 Docker 列表溢出，不沿用按容器总数增加最小高度的规则。
- **文字与单位**：正式 UI 使用英文，百分比、GiB/TiB、°C、W、tok/s、req/s 或 seq/s、秒等单位明确。请求/处理单元计数须标明实际语义，不混用 HTTP 请求与内部序列。正式界面不出现 MOCK DATA、UI CONCEPT 或设计预览提示。

## 需求说明

### REQ-001 命令启动、配置、全屏运行与错误日志

**需求说明与预期行为**

项目使用 uv 安装。首次完成工具 PATH 配置并准备有效用户配置后，可在新终端直接运行 `joi-observer`，无需手动激活虚拟环境，也不必进入源码目录；命令直接进入全屏 TUI，无需浏览器或菜单选择。标题显示 `Joi::Observer`；主机信息右侧显示被监控主机的当前时间。硬件、容器与模型数据持续刷新，`q` 退出并恢复终端。

配置可指定多个模型监控项，支持 Chat、Embedding、Reranker 类型；每项有稳定标识、模型类型、展示名称及直接采集的 vLLM 服务地址。同名模型位于不同服务时应可区分，不自动合并。监控项顺序由配置决定。提供覆盖当前三个部署模型的可修改示例配置与使用说明，用户先复制并修改为实际使用的 `config.yaml`。缺少配置时，在进入全屏前提示期望的配置路径及示例位置并退出，不使用随包目标直接启动；示例中的部署值须标明来源，不通过 LiteLLM 自动发现或转发采集。

**采集失败日志**

- 在 `config.yaml` 中自定义日志目录，默认 `~/.joi-observer/`，日志文件名为 `error.log`，因此默认完整路径为 `~/.joi-observer/error.log`。`~` 按运行用户的主目录展开；支持自定义绝对目录，目录不存在时自动创建。不修改原配置文件，也不自动切换到 XDG、临时目录或项目源码目录。
- 采集错误首次发生时立即记录一条 `ERROR`，包含服务器本地发生时间（不附带时区信息）、采集器、监控对象标识、错误类型与原因。同一采集器、同一对象的相同错误持续出现时，相邻记录至少间隔 60 秒；不同对象或新的错误立即记录，不能被其他错误的间隔限制。仅限制日志写入频率，不降低采样或 UI 更新频率。对象恢复正常后再次失败，视为新一轮故障，立即记录；恢复本身不记日志。相同错误的归类规则由 R2 明确，不能因动态时间等无关文本变化而绕过限制。
- 只记录诊断所需信息，不保存正常指标快照、Token 内容、模型输入输出或凭据。
- 不记录正常采样、启动/退出、采集成功或恢复信息，不增加 INFO/WARNING/DEBUG 日志。已知不适用/不支持字段不作为失败记录；超时、权限不足、无法取得配置对象、响应解析失败等实际采集失败才记 ERROR。
- 使用按大小轮转的追加日志。默认单文件阈值为 10 MB，保留 3 份备份；阈值和备份数量可在 `config.yaml` 调整，达到容量后淘汰最旧备份，避免无限增长。
- 日志只写文件，不将日志、异常文本或堆栈输出到 TUI，也不通过 stdout/stderr 干扰全屏界面。退出 TUI 后也不补打采集错误。正常 TUI 绘制不受这条日志输出限制影响。
- 进入全屏前检查日志目录/文件可写性；目录不可写、无法创建或无法打开日志文件时，仅在进入 TUI 前提示一次，然后继续启动监控，暂不写日志，不反复提示。后续采集失败需要记录时可重试初始化/写入；恢复可写后继续记录后续错误，不要求补写未能落盘的记录。运行中日志写入失败不得改变 TUI 布局、打印错误或停止其他采集。

**边界与约束**

- 缺少可选监控项时展示对应空态，其余面板仍可用。
- 缺少配置、配置格式错误、重复标识或非法采样间隔等，在进入全屏前给出可定位的命令行错误并退出，不进入半初始化 TUI；这不属于采集失败日志，不写入 error.log。日志目录/文件无法初始化按上文提示一次后继续，不归入阻断启动的配置错误。
- 不自动安装驱动、配置 Docker 权限、修改系统或部署模型。
- uv 安装与首次工具 PATH 配置的具体步骤、CLI 参数细节、非交互终端处理及最小终端尺寸由 R2 定义；不得要求普通启动先连接网页。

### REQ-002 本机硬件总览

**需求说明与预期行为**

上半区左侧列出检测到的 NVIDIA GPU，逐卡显示标识/名称、利用率、已用/总显存、温度和当前功耗。右侧依次显示 Host Resources、Storage、Docker；Host Resources 显示整机 CPU 利用率和 RAM 已用/总量、使用率。

Storage 显示配置挂载点的已用/总容量及使用率，默认 `/`、`/data`。内容区固定 3 行，标题和边框另计；按配置顺序仅采集和显示前 3 个挂载点，每项占 1 行，不足 3 项时保留剩余内容行，0 项时在这一区域内显示空态。第 4 项起忽略，不报超量错误、不采集、不显示，也不修改原配置文件；前 3 项中某项不可用时不以第 4 项补位。按挂载点观察文件系统容量；当 `/data` 未挂载时，该项采集失败，预留状态位显示 STALE，原因仅写 ERROR 日志，不能拿根文件系统容量冒充 `/data`。

- 设备名称和总容量来自有效采集，不使用设计稿的固定 GPU 型号、容量或利用率。
- GPU 分组、用途、模型关联信息仅可来自显式配置或可靠数据。上下切换模型时，按已知映射更新关联 GPU 的高亮；关联卡的编号、利用率条已填充段及百分比用主题主色，未关联卡对应位置用灰色。映射未知时不显示关联高亮，不根据型号、利用率或显存占用猜测；未知的分组和用途说明省略。全部 GPU 保持原顺序和布局，不因模型选择被过滤、重排或触发重新采集。

### REQ-003 指定 Docker 容器状态

**需求说明与预期行为**

采集用户配置的全部容器，不设固定数量上限。显示时按配置顺序取 Docker 内容区域可容纳的前若干个容器，每个占 1 行；剩余容器不显示，不作任何提示。生命周期状态使用首字母大写、其余小写，例如 Running、Exited、Restarting、Paused、Created、Dead。正常查到停止状态仍显示 Exited；找不到配置容器、无法访问 Docker 或权限不足时，可见行的状态原位替换为 STALE，具体原因仅写 ERROR 日志。首版不额外展示 healthcheck 结果、错误原因或输出；Running 只代表生命周期状态，不保证应用健康。

**边界与约束**

- 容器配置数量没有固定上限，全部指定对象均保留并参与采集；不得截断配置或采集对象列表，也不因显示容量不足而报配置错误。只有显示层按当前可用行数隐藏后续条目，不修改原配置文件。
- Docker 面板高度由上半区右侧剩余可用空间决定，余高允许留白。内容区域可容纳 N 行时，仅显示配置中的前 N 项（不足 N 项时全部显示）；无可用内容行时不显示容器条目。剩余项不提示、不显示省略号或“更多/隐藏数量”标记，不触发放大提示、不新增滚动或分页、不侵占下半区，其他面板继续正常显示。
- 放大窗口后按新的可用行数显示更多配置项，缩小后隐藏末尾项，顺序始终与配置一致；隐藏项仍采集，重新可见时使用当前状态。采集失败、停止或重启不改变条目的位置，不用后续容器替换前面的失败项。单纯因为显示不下而隐藏不属于采集失败，不记录 ERROR。
- 按显式配置的容器身份识别，不默认监控所有容器，也不把部署文档中的 Compose 项目名称直接当作容器名称。
- 容器生命周期状态与服务业务负载独立。Chat、Embedding、Reranker 的模型指标由 REQ-004 定义；WebUI 可作为普通容器监控，但不采集其业务指标。
- 不提供容器 CPU/RAM/日志/网络指标，不进行启停或重启操作。

**验收标准**

| 编号 | 可观察的验收条件 |
| --- | --- |
| AC-301 | 分别配置 1、5、6、10 个容器，配置和采集均保留全部对象，不因超过 5 个而报错或截断；显示配置顺序中区域可容纳的前若干项，状态采用 Running、Exited 等格式，未配置的容器不出现。 |
| AC-302 | 成功查到的停止容器显示 Exited 且不记错误；配置容器不存在、Docker 不可用或权限不足时，相关行统一显示 STALE，日志中区分原因，UI 不显示原因、不增加行数。 |

### REQ-004 vLLM 多类型模型负载与历史

**需求说明与预期行为**

根据配置持续采集并展示 Chat、Embedding、Reranker 三个已部署模型；未选中的模型也持续采集。下半区左侧列出模型、类型、采集状态及运行/等待数量，右侧立即展示选中模型适用的指标和最近约 60 秒吞吐柱状历史，无需进入独立详情页。

当前部署对象依据本地材料如下；名称与地址可配置，不硬编码，也不表示本次已验证端点在线：

| 模型类型 | 部署模型名 | vLLM 服务地址 |
| --- | --- | --- |
| Chat | `qwen3.8-flash-next` | `127.0.0.1:8000` |
| Embedding | `qwen3-embedding-4b` | `127.0.0.1:8001` |
| Reranker | `qwen3-reranker-0.6b` | `127.0.0.1:8002` |

**按模型类型展示的指标**

| 指标 | Chat | Embedding | Reranker |
| --- | --- | --- | --- |
| 采集失败状态 | 原位 STALE，不显示时间或原因 | 原位 STALE，不显示时间或原因 | 原位 STALE，不显示时间或原因 |
| RUNNING / WAITING / Total | 运行、等待及总数量 | 运行、等待及总数量，注明处理单位 | 运行、等待及总数量，注明处理单位 |
| 主要吞吐 | DECODE / tok/s、PREFILL / tok/s | RATE：完成处理单元/s，单位依可靠来源确定 | RATE：完成处理单元/s，单位依可靠来源确定 |
| 首 Token 延迟 | TTFT / s | 不适用 | 不适用 |
| 平均排队时间 | Avg queue / s | Avg queue / s | Avg queue / s |
| 平均完成延迟 | 本期不增加此项 | Avg latency / s | Avg latency / s |
| KV CACHE / % | 展示模型服务报告值 | 当前 pooling 部署不作为必需指标，省略或 N/A | 当前 pooling 部署不作为必需指标，省略或 N/A |
| 约 60 秒历史 | DECODE HISTORY / tok/s | RATE HISTORY，与该模型 RATE 单位一致 | RATE HISTORY，与该模型 RATE 单位一致 |

**指标业务口径**

- RUNNING/WAITING 表示 vLLM 报告的当前执行/等待数量，不是累计完成量，不包含 LiteLLM 中尚未进入 vLLM 的队列。Total 仅对同一快照、相同单位的 RUNNING + WAITING 求和；任一值未知时不伪造总数。
- Chat 的 DECODE/PREFILL 分别为最近两个可比较有效采样点间的生成/输入 Token 增量除以实际时间差；沿用来源的 Token 计数口径，不推断计算耗时。
- Embedding/Reranker 的 RATE 为同一区间内已完成处理单元的增量除以实际时间差。只有来源明确计数完整 HTTP 请求时才显示 req/s；若计数内部推理序列则使用 seq/s 并说明单位，不标成 HTTP 请求率。R2 须固定每类模型的映射及标签；来源单位不明时显示不可用，不能猜测换算。
- 一次 Embedding 调用可包含多条输入，一次 Reranker 调用可包含多个候选。HTTP 请求、输入条目、候选对、内部序列不是默认等价的计数单位；不能从批大小、top_n、配置并发上限反推实时请求率，不能把返回结果数直接当完成量。
- TTFT 是 Chat 首 Token 延迟。Avg queue 是来源已记录的处理单元排队时间，不是仍在队列中的任务当前已等待多久。Embedding/Reranker 的 Avg latency 是来源记录的处理单元从接收到完成的耗时；计时范围写入使用说明，UI 仅保留准确的简短指标名称与单位，不新增解释行。若来源只覆盖引擎内处理，不能声称是完整 HTTP 响应耗时，更不能包含未采集的网关或客户端时间。若只有执行耗时，不得改名冒充完成延迟。
- 所有延迟采用最近 60 秒内有效观测的总时长除以相应观测数，不对每秒均值作无权重平均；各指标使用自身的计数和处理单位。启动不足 60 秒时使用已有的可比较区间；历史通过现有时间轴体现实际范围，不额外显示“窗口不足”等诊断说明。无观测显示 `—`。失败后的窗口只使用可验证的观测范围，不能把无法覆盖的区间呈现为完整窗口。
- Chat 的 KV Cache 使用率来自该模型服务，不等同 GPU 显存占比。Embedding/Reranker 不套用 Chat 的生成 Token 速率、TTFT 或 KV Cache；不适用项省略或 N/A，不显示 0。可选的输入 Token 指标只有来源含义明确时展示，名称必须反映输入处理，不能称为生成吞吐。
- 三类模型历史均按各自的主要吞吐指标与单位展示；不足 60 秒时显示实际已有区间，切换模型不改变其他模型的历史。

模型名称、服务端口/地址可作为路由信息显示。并发上限、总请求上限、TP/EP、量化方式、上下文长度等只在明确配置或可靠采集时显示；未知时省略相关附加信息和分母，不沿用稿中的 `3`、`15` 等常量。

**边界与约束**

- 首版覆盖三个已部署的 Chat、Embedding、Reranker 模型。直接采集各自 vLLM 服务，不访问 LiteLLM 接口、不采集其队列/吞吐/延迟，也不将 LiteLLM 列为模型或采集依赖；不采集 WebUI 用户活动或其他服务业务指标。
- 不自动合并不同端点的同名模型。配置服务与所报告模型不匹配时按采集失败处理，UI 仅原位显示 STALE，原因写 ERROR 日志，不能展示其他模型的数据。
- 首版以本地材料记载的 vLLM v0.31.0 为兼容性核对目标，不承诺所有历史/未来版本。R2 必须分别核对生成与 pooling 模式的真实指标名、标签、单位、多引擎汇总语义及可用性，R1 不假设 Chat 的指标在另外两类模型上均存在。

### REQ-005 下半区模型导航与服务入口

**需求说明与预期行为**

默认进入 vLLM 服务，下半区选择配置中的第一个模型。`↑`、`↓` 可在 Chat、Embedding、Reranker 模型间移动选择，并同步对应指标布局、单位、历史及上半区关联 GPU 高亮；到列表首尾时停留，不循环。无模型时显示英文空态，方向键不报错。刷新保留当前选择，模型不可用也不自动跳走。

底部保留 `vLLM` / `WebUI` 两个服务入口；vLLM 为当前项，WebUI 清楚标记为禁用/计划中。服务切换位及其下方键位提示均计入页面下半区的一半高度，不在服务窗口之外额外扩大下半区占比。原始“左后方向键”按“左右方向键”理解；经用户澄清，首版只有 vLLM 可用，因此 `←`、`→` 均不切换服务，未来启用其他服务时再定义切换行为。

**边界与约束**

- 方向键直接控制下半区的模型选择，并联动已知关联 GPU 的高亮；不直接选择 GPU、不滚动硬件区、不更改数据源，不过滤或重排 GPU，不改变布局与采样。
- `q` 为全局退出、`t` 为全局主题切换，不受模型列表状态或采集错误影响。
- 首版采用键盘操作，不引入需要鼠标完成的流程。Theme 明确不可点击；模型/服务项无需实现鼠标操作。
- 不实现 Enter 详情、p 暂停、Tab 面板切换或其他概念稿的交互。按 Enter/p 不应打开详情或暂停采样。

| AC-501 | ↑↓ 可遍历 Chat、Embedding、Reranker，详情、指标适用性、单位和历史随类型切换，并按已知映射同步 GPU 关联高亮；连续刷新不重置模型选择，首尾不循环，方向键不直接选择或滚动硬件区。 |

### REQ-006 Neon Grid 外观与双主题

**需求说明与预期行为**

以 Neon Grid 为唯一主布局参考，采用深色、等宽、紧凑分区。按共同页面分区规则将全页分为上下两半：下半包括服务窗口、服务切换位和键位提示，上半包括品牌/主机信息与硬件区域等。允许为终端字符尺寸、真实字段和不可用状态调整细节，不照搬浏览器像素布局。采集状态变化遵守共同布局稳定规则，预留固定状态位置；模型详情可复用原 READY/QUEUED 位置显示 STALE，其他面板/行也不得因故障增加空间。

右上角显示 `Theme: Moonlight` 或 `Theme: Hologram` 并提示 `t`；这是状态展示，不是可点击按钮。每次 `t` 在两种主题间切换，全屏相关颜色立即更新，模型选择、监控状态和历史保持。每次启动默认 Moonlight，不写入主题偏好。

| 颜色角色 | Moonlight | Hologram |
| --- | --- | --- |
| 背景 | `#080E18` | `#080E18` |
| 正文 | `#D4DDEB` | `#D4DDEB` |
| 次要信息 | `#8A9DB5` | `#8A9DB5` |
| 主色 | `#7DDFFF` | `#7B9FFF` |
| 辅色 | `#C6A7FF` | `#E570D0` |
| 排队强调 | `#FFA45B` | `#FFA45B` |

具体视觉规则：

- 品牌 `Joi` 用辅色，`::` 用灰色，`Observer` 用主色。主机时间位于主机信息右侧。
- GPU 利用率分段条约占可用行宽的一半，百分比紧随条末。选中模型关联的 GPU 编号、利用率条已填充段及百分比用主题主色，未关联卡对应位置用灰色；映射未知时不显示关联高亮。显存始终用灰色。
- CPU/RAM 条用辅色；未填充段与 GPU 条共用灰色。RAM 已用量灰色、总量白色。
- 上半区右侧按 Host Resources、Storage、Docker 顺序排列。Storage 固定 3 行内容，标题和边框另计；Host Resources 满足其内容高度后，剩余高度分配给 Docker。Docker 按配置顺序显示内容区可容纳的容器，每个占 1 行，额外空间可留白；剩余容器不显示且不作任何提示，不再由 Storage 吸收余高。
- vLLM 标题与路由信息用辅色，选中模型用主色；`Total`、`Avg queue` 保留这些文案。设计中的“紫色/冰蓝”按主题角色变化。
- 仅 `QUEUED` 和大于 0 的等待数量使用琥珀色；`WAITING` 标签和等待值 0 用普通正文色，不加感叹号。采集失败只显示 STALE，正常采集到的 Exited/Restarting 等仍显示其生命周期状态，使用正文/次要色，不扩大琥珀用途，不添加错误原因或额外说明。
- 底部英文键位提示用主色；没有 Details/Pause，也没有设计预览模拟标记。
