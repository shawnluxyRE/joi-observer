## 已确认合理的部分

服务独占配置、采集器、Monitor、MonitorState 和日志，TUI/Web 只读取不可变快照，符合单一采集源要求。一次启动加载配置、服务实例身份、完整元数据配对、客户端无自动重连、来源 STALE 与整体失联区分、先恢复终端再输出错误、客户端会话独立及 Unix 本机只读权限方案均与 REQ-001 一致。

现有采集解析、Monitor 调度、State 计算和错误日志没有为了进程拆分而重写业务算法；视图继续复用原布局、帧调度、主题、导航、精度和历史逻辑。这是保留已有功能与回归断言的正确方向。首版提出的问题已按上表落实到当前设计和测试。

## 发现与处理要求

### R2-REV-001 / P1：完整快照上限会使合法配置停止采集

位置：[IPC 设计](../../../design/ipc.md) 的帧大小与超限规则（当前第 61、71 行），以及[服务设计](../../../design/collector-service.md)的发布主任务失败结束服务规则（当前第 63 行）。

当前方案把 **8 MiB 限制应用于完整元数据及全部约 60 秒历史**。配置并不限制模型/容器数量，采样允许 0.1 秒；完整历史为每个模型最多约 601 点。合法对象较多时，逐渐积累历史即可超过上限。发布失败随后结束整个服务，systemd 可能重新启动它，造成周期性历史重置，而不是连续采集。

本地 WSL 离线测量使用真实 MonitorState、VllmSpec 与合法 ChatEngineSample，按公开 JSON 字段投影，并未调用或伪造待实现 codec。单模型完整文档 410870 字节；21 个模型为 **8623912 字节**，超过 8388608 字节上限，且尚未计入实际宿主硬件。测量脚本、实际输出及参数见 `evidence/measure_snapshot_size.py` 与 `evidence/measure-snapshot-size.json`。测量描述的是该协议表示的字节量，不代表发布业务已实现。命令为 WSL 中 `/home/shawn/projects/tmp/joi-observer-dev-0-venv/bin/python /mnt/d/Documents/joi-observer/docs/dev-workflow/dev-1/REQ-001/evidence/measure_snapshot_size.py /mnt/d/Documents/joi-observer`。

首版修订建议：不能通过截断对象/历史、停止 Monitor 或新增隐式配置数量限制解决。当时提出过应用层分片选项；经用户讨论，最终采用更简单的有序流分批读写，取消该选项。发布/客户端故障必须与持续采集隔离。只调大常量不能消除与配置规则的根本冲突。

需补充：超过原 8 MiB 的完整快照往返保真；分片不完整不安装缓存；大配置运行超过一个历史窗口仍持续采样；慢客户端隔离。同步协议、server/client/service 注释、现有超限测试及新用例。

### R2-REV-002 / P2：固定一秒发布降低原有快采样的展示时效

位置：[IPC 设计](../../../design/ipc.md)当前第 62 行、[服务设计](../../../design/collector-service.md)当前第 64、75 行；对照配置的 0.1～60 秒采样范围与 `tui/app.py` 每帧读取快照行为。

原 TUI 可在下一 UI 帧看到 State 的新值。固定每秒发布将 0.1 秒采样的最新指标限制到 1 Hz；在两次发布之间出现又恢复的 STALE/WAITING 等状态可能从未进入指标槽。历史包含缺口并不等于保留原来的最新状态展示行为。现有快采样运行期测试还在约 0.75 秒内等待真实指标可见，不能通过延长等待来掩盖这一降频。

修订要求：将一秒定义为无变化时的心跳间隔，数据发布由状态更新或不低于有效采样节奏的机制驱动；同轮更新可以合并，单次编码共享给读者，客户端数量不能反向影响采样。明确更新到发布的时效边界，以及旧待发完整快照被新快照替换的规则。

需补充：0.1 秒采样时，在健康内存传输下新值及时可见；跨发布边界的短暂失败/恢复不被固定一秒节奏系统性吞掉；多个客户端仍只采一次；无来源更新时心跳保持连接。

### R2-REV-003 / P2：分段测试尚不能证明新链路保留全部业务语义

目前新增服务测试使用离线 CPU 来源，协议测试使用手工完整快照，客户端测试使用独立字节夹具。它们各自有效，但没有一项将已有硬件/Docker/vLLM 原始样本经真实采集器、Monitor、State、codec、SnapshotClient、ObserverApp 的新链路贯通后比较原有指标及画面断言。

还需保留极大整数边界：原 `test_vllm_view.py` 包含 `10**10000`，`test_hardware_view_edges.py`、`test_state_monitor_edges.py` 包含 `10**5000`；新协议目前仅用 `2**53+1` 验证精度。Python 3.12 默认 JSON 的十进制整数转换限制会使直接 dumps/loads 在超过 4300 位时失败。不能让原来可表示/显示的值在经过 IPC 后变成失联，也不能把这些测试降成小整数来避开问题。

修订要求：固定极大整数的受控线格式与验证方法，不修改业务数值、不全局关闭解释器的转换限制。复用原始离线来源 fixture，新增一组完整内存传输链路的行为等价测试，比较指标、单位、0/未知/N/A、STALE/缺口、对象顺序/GPU 关联及画面关键断言。该测试必须触达真实业务入口，不模拟 codec 或客户端业务结果。

## 原功能和测试能保留到什么程度

| 范围 | 保留要求 |
| --- | --- |
| 配置校验、采集解析、身份、数值计算、单位、60 秒窗口、错误日志 | 业务逻辑和有效断言保持；配置只加载一次的归属迁到服务 |
| 布局、主题、导航、数字精度、未知/N/A、历史扫描、GPU 关联 | 保留纯函数与有效断言，输入装配可从 AppConfig 转为展示元数据 |
| 默认命令、`--config`、运行期组合根、退出清理 | 生产入口和测试装配必须迁移；TUI q 只关客户端，原采集清理断言移到服务 stop 场景 |
| 模型详情标题 | 按 AC-114 必须改变，列表仍 name，详情 served_model_name 或 name 回退；这是确认的行为变化 |

不能承诺全部旧测试文件或预期文本一字不改。一个明确冲突是 `tests/test_vllm_view.py` 当前第 284～305 行：同一模型配置了 `name=Flash-Next`、`served_model_name=upstream-model`，旧用例要求两处都显示 Flash-Next，且 upstream-model 不出现；这与 AC-114 直接相反。

该用例应只迁移标题预期，同时保留稳定 id 匹配、13/17/Total 30、QUEUED、忽略错误身份对象及输入不可变断言。不得让 AppConfig 和 DisplayMetadata 输入故意产生不同的正式标题语义，以维持旧断言表面通过。

原组合根相关测试分布于 `test_cli`、`test_docker_integration`、`test_hardware_runtime`、`test_local_hardware_io_edges`、`test_navigation_app`、`test_shell_edges`、`test_tui`、`test_vllm_integration`、`test_vllm_runtime`，以及入口相关 PTY 测试。多数只迁移装配点；例如硬件测试原来“q 后所有 IO 关闭”，应分解为“客户端 q 后后台 IO/另一客户端继续”和“服务 stop 后所有采集 IO 回收”。原来的清理验证不能删掉。

## 证据与结论边界

- 首版复查只读核对需求、设计、接口、原实现及新旧测试；当时 `git diff -- tests` 确认旧测试未改。随后用户批准本次修订，现已按配置下限和详情标题的新行为迁移对应预期，其余验证逻辑保留。
- 引用上轮实际 WSL 结果：既有 2037 全部通过，新增 91 项中 1 通过、90 项因骨架/迁移未实现失败。未重跑完全相同的业务测试来冒充新架构验证。
- 旧 main/ApplicationRuntime 仍在执行，所以“2037 通过”证明当前改动未破坏旧实现，不能推导为拆分实现完成后一定兼容。
- 新的定量验证只在本地 WSL 使用内存对象及 JSON 字节计算，不启动或连接任何服务器。
- 当前结论是**核心功能与测试判断可以保留，接口装配及已确认变化对应的预期必须迁移**。上述三项已有 R2 产物与测试入口；最终基线和交接状态见 handoff-r2.md，不把业务尚未实现写成已通过功能验收。
